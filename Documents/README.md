### プレイ時間と展示の方針

本作はプレイ時間が長くなることを許容する。
ただし展示ブースでは長時間の占有ができないため、**短時間で切り上げられる遊び方を用意する**こと。
具体的な作り方は下の「ビルドの作り方」に従う。

展示ブースには必ず担当者が在席するため、無人時の自動タイトル復帰は必須ではない。

### ビルドの作り方（2026年8月31日・決定）

> **ビルドを切り替える仕組みは作らない。ビルドは常にまるまる1本を作る。**
> 以前あった Scripting Define Symbols（`EXHIBITION_BUILD`）で切り替える案は**採用しない**。

| やりたいこと | どうするか |
| --- | --- |
| **チュートリアルを短時間で遊んでもらう** | **セレクト画面からチュートリアルを選べるようにする。** ビルドは切り替えず、まるまる1本を作る |
| **体験版を配る** | **ブランチを分けて、そのブランチ側で要素を削る。** それもまるまるビルドする |

つまり、**プログラム側にビルド種別の分岐を入れる必要はない。**
チュートリアルは「セレクト画面から選べる遊びの1つ」として、通常の機能と同じように作ればよい。

> **企画が未定のため、チュートリアルを作るかどうかもまだ決まっていない。**
> ただし作る場合の作り方は上記で確定しているので、**分岐の仕組みを先回りして実装しないこと。**

> **体験版ブランチを作るときの注意（実施時に読む）**
> 要素を削ったブランチは、本編から**枝分かれしたまま離れていく**。
> 本編側でバグを直しても、体験版ブランチには自動では入らない。
> 体験版を作ると決めた時点で、**いつ枝分かれさせるか**と**本編の修正をどう取り込むか**を大槻 海斗と決めること。

### ファイル名の付け方（場所によって違う）

**読む相手が「人」か「Unity」かで分ける。**

| 場所 | 名前の付け方 | 理由 |
| --- | --- | --- |
| `Documents/` | **日本語**。中身が一目で分かる名前にする（例：`制作ログ.md`） | 全員が読む場所だから。英語の略語（`DevLog` `RiskList` など）は使わない |
| `Mirai01/Assets/` | **半角の英数字**。日本語もスペースも使わない（例：`PlayerMove.cs`） | Unity（ゲームエンジン）が直接読み込む場所であり、**半角英数字のほうが不具合が起きにくい**ため |

`Assets/` の中では、単語の区切りを大文字にする（`PlayerMove` のように）。
また、**C#スクリプトのファイル名は中のクラス名と必ず同じ**にすること。違うとUnityが認識しない。

> `Mirai01/Assets/` の中の構成は、まだ全体が決まっていない。
> AIは `Assets/` 以下に新しいフォルダを勝手に作らず、**置き場所を確認してから**作業すること。
> ただし**検証用シーンの置き場所は `Assets/Scenes/Test/` に決まっている**
> （`Documents/シーンとプレハブの作り方.md`）。

## 初回セットアップ手順

1. **Unity Hub** をインストールする。
2. Unity Hub から **Unity 6000.3.14f1** をインストールする。
   - モジュールは、作るプラットフォームに合わせて選ぶ（PC向けなら追加モジュールは基本不要）。
3. **Git** をインストールする（Windowsなら [Git for Windows](https://gitforwindows.org/)）。
   インストールしたら、日本語のファイル名が文字化けしないよう、次のコマンドを1回だけ実行しておく。

   ```bash
   git config --global core.quotepath false
   ```

4. リポジトリを取得する。置き場所はパスに**日本語や空白を含まない場所**を推奨する。

   ```bash
   git clone https://github.com/Sand639/Mirai01.git
   ```

5. Unity Hub の「プロジェクトを開く」で、`Mirai01/Mirai01`（`Assets` が入っている方）フォルダを選ぶ。
   - リポジトリのルートを選ぶと開けないので注意。
6. 初回起動はライブラリ生成のため時間がかかる。エラーが出た場合はリーダーかAIに相談すること。
7. `Assets/Scenes/SampleScene.unity` が開ければ成功。

> `Library/` や `Temp/` などUnityが自動生成するフォルダはGitに含めない設定になっている（`.gitignore` 済み）。
> 「Gitに出てこないファイルがある」と感じても、それは正常な場合が多い。

## 毎日の作業の流れ

セットアップが終わったら、**2回目以降は毎回この順番**で作業する。
コマンドを覚える必要はない。**AIに「最新を取ってきて」「今の変更をコミットしてプッシュして」と頼めばやってくれる。**

### 1. 作業を始める前に、最新を取ってくる

**Unityを閉じた状態で**行う。開いたまま取り込むと、Unityが古い状態を握ったままになり不具合の原因になる。

```bash
git pull
```

> ここを飛ばすと、他の人の変更と衝突（コンフリクト）しやすくなる。**一番大事な手順。**

### 2. Unityを開いて作業する

シーン（`.unity`）やプレハブ（`.prefab`）を触るときは、**先にDiscordで一声かける**。
これらは2人が同時に編集すると、片方の作業が消える。

> プログラマーは、**新しい機能は新しいシーンに作る**こと。詳しくは `Documents/シーンとプレハブの作り方.md`。
> そもそも人と同じシーンを触らない形にしておけば、一声かける場面自体が減る。

### 3. 区切りがついたら保存する（コミット・プッシュ）

Unityで **Ctrl+S** を押してシーンを保存してから行う。保存していない変更はGitに記録されない。

```bash
git add -A
```

```bash
git commit -m "何をしたかを書く"
```

```bash
git push
```

> **こまめにやってよい。** 完成していなくても、区切りごとに保存しておくと、失敗しても戻れる。

### 4. 記録を残す

機能を追加したら `Documents/制作ログ.md` に1行、詳細は `Documents/機能ドキュメント/` に1ファイル追加する。
**これもAIに頼んでよい。**

### 困ったときは

| こうなった | どうする |
| --- | --- |
| `git pull` でエラーが出た | **自分で解決しようとしない。** 画面に出た文章をそのままAIか大槻さんに見せる |
| コンフリクトと言われた | 同上。どのファイルが衝突したかを伝えれば対応できる |
| 自分の変更が消えた気がする | **まだ何もせず**に相談する。コミットしてあれば戻せることが多い |
| Unityが「新しいバージョンで開く？」と聞いてきた | **絶対に承諾しない。** キャンセルして大槻さんに連絡する |

### 2. 初めての人にだけ説明する

「このプロジェクトでAIを使うのは初めてですか？」と尋ね、**初めての場合のみ**以下を説明する。
**毎回説明しないこと。**

- Codex / Claude Codeのような「フォルダを参照して自分でファイルを編集・作成するAI」も、ChatGPTやGeminiのようなチャットAIも、**頼み方の基本は変わらない**ということ。
  ただし前者は実際にファイルが書き換わるため、**作業後は必ずGitで差分を確認してから次に進むこと**。この違いは必ず伝えること。
- Codex / Claude Codeの導入方法と、日々の使い方
- Git Flowの考え方と、このプロジェクトでの運用（後述の「Gitについて」を参照）
- 分からないことがあった時、誰に聞けばいいか

この他にも質問が来れば丁寧に教えること。専門用語はできるだけ使わず、必要なら例えを用いて説明すること。

## AIへの頼み方（メンバー向け）

実装を頼む時は、次の3点を伝えると精度が上がる。

1. **何を作りたいか**（機能の目的）
2. **どのファイル、どのシーンに関係するか**
3. **何ができれば完成と言えるか**

### 依頼文のテンプレート

```
【やりたいこと】プレイヤーが2段ジャンプできるようにしたい
【関係する場所】Assets/Scripts/Player 付近 / SampleScene
【完成の条件】空中で1回だけ追加でジャンプでき、着地したら回数がリセットされる
```

Gitに慣れていない場合、ブランチの作成やマージはAIに頼んでよい。コマンドを覚えていなくても作業できるようにしている。

### `Auto:` … AIに自分で動き続けてもらう

「バグを探して」「改善点を探して」のように、**終わりがはっきりしない作業**を任せたいときは、
指示の先頭に `Auto:` を付ける。

```
Auto: バグを探して
Auto: 改善点を探して
```

> **`/Auto` と書ける環境もある。**
> ターミナルで動かすClaude Codeでは `/Auto 改善点を探して` とも書ける。
> ただし**アプリ版のClaude CodeやCodexでは、`/` で始まる入力がコマンドとして処理されてしまい届かない**。
> どの環境でも確実に通るのは `Auto:` のほうなので、**迷ったらこちらを使う**。

AIは次のように動く。

1. 作業前に、**その指示をどう受け取ったか**と、**継続基準**（どうなったら終わりにするか）を宣言する。
   例：「『バグを探して』は動かなくなる箇所を先に潰したいという意図と推測されるため、
   スクリプトを順に読み、見つけたバグを `リスクリスト.md` にまとめます。
   未確認のスクリプトが無くなるまで続けます。」
2. こちらから基準を伝えた場合は、**そちらが優先される**。
   例：`Auto: バグを探して 3周したら止めて`
3. **新しいブランチを切って**作業する。今やっている作業が壊されることはない。
4. 作業中は確認を取らずに進むが、ファイルを編集するたびに**何をしたかを一言報告する**。
5. **こまめにコミットする。** 不具合が起きても、コミットした時点まですぐ戻せる。
6. 次のいずれかで終了する。
   - **止めて**と言ったとき
   - 宣言した継続基準を満たしたとき
   - 使えるクレジット（利用上限）が尽きたとき
7. 終了時に、結果のまとめと**使ったブランチ名**が報告される。取り込むかどうかはこちらが決める。

途中で判断に迷うことがあっても止まらず、`質問リスト.md` に質問を書き残して先に進む。
また、指示の言葉どおりに動くだけでなく、**その指示で本当に欲しかったもの**を考えて成果を残す。
「バグを探して」であれば、見つけたバグの場所・再現条件・影響・直し方の案が `リスクリスト.md` にまとまる。

> **止めたいときは、いつでも「止めて」と言えばよい。**

## AIの注意事項

### メンバー情報の追記

- メンバーが自分の名前を伝えてきた場合、このREADMEのメンバー構成に追記すること。
- その際、役職（プログラマー／デザイナー／プランナー）が分からなければ確認すること。
- 追記したら**変更記録にも一行追加**すること。

### ドキュメントの更新

`Documents/` 配下は**主にAIが読み書きする場所**である。人間が目を通すのはたまにでよい。

- `Documents/` 配下のドキュメントは、**いちいち確認を取らずに自動で変更してよい**。
- 変更点や改善点がある場合は、そのドキュメントの**一番下の変更ログに1行足したうえで**更新すること。
- ただし `Mirai01/Assets/` 以下のファイルは、指示された内容の範囲でのみ編集すること。

#### ドキュメントは自由に使ってよい

`Documents/` は、**AIが自分たちのために使ってよい場所**でもある。
次のようなことは、いちいち許可を取らずにやってよい。

- 作業していて「このサイクルはこう変えたほうがいい」と気づいたことを書き残す
- 失敗した手順を「こうやって失敗したので気をつけて」と、**後から来る別のAIに向けて**残す
- うまくいったやり方、詰まりやすい場所、環境の癖などをメモする
- **AI同士が読み書きするためのドキュメントを新しく作る**
- 既存のドキュメントが使いにくければ、構成を作り変える

置き場として `Documents/AIの申し送り.md` を用意してある。足りなければ**新しいファイルを作ってよい**。

このプロジェクトでは、複数のAIが別々のPCで、別々のメンバーの隣で作業する。
**同じ失敗を別のAIが繰り返さないように残しておくこと**は、実装と同じくらい価値がある。

守るのは次の2つだけ。

- 変更したファイルの**変更ログに1行足す**
- このREADMEの**ルールに関わる部分**を変えたときは、変更ログに残すだけでなく、
  **チャットでも何を変えたか必ず伝える**（人間が把握できなくなるため）

#### 変更があったら「みんなの作業状況」として伝える

作業を始めるとき（`git pull` のあとなど）に `Documents/` のファイルが**前回から変わっていた**場合、
それは**他のメンバーが作業した記録**である。AIは作業に入る前に、その内容を要約してユーザーに伝えること。

- 見る場所 … `制作ログ.md`（追加された機能）、`リスクリスト.md`（増えた不安箇所）、
  `質問リスト.md`（新しい質問と回答）、`機能ドキュメント/`（増えたファイル）、`AIの申し送り.md`（他のAIからの申し送り）
- 伝え方 … 「前回から、○○さんが△△を追加しています」のように、**誰が・何をしたか**が分かる短いまとめ
- 調べ方の例：

  ```bash
  git log --oneline -- Documents/
  ```

- これから触る予定のファイルやシーンが他の人の作業に含まれていた場合は、**必ず先にその旨を伝える**こと。

### Gitについて

このプロジェクトは **Git Flow** に沿って運用する。メンバー全員がGitに習熟しているとは限らないため、AIはブランチ操作のサポートを行うこと。

**ブランチの役割**

| ブランチ | 役割 |
| --- | --- |
| `main` | 展示・配布に出す完成版。直接編集しない |
| `develop` | 開発の合流先。日々の作業はここに集まる（**未作成。大槻 海斗が作成し、あわせて全員に使い方を説明する**） |
| `feature/機能名` | 機能ごとの作業ブランチ。例：`feature/player-move` |
| `release/x.x` | マスターアップ前の調整用 |
| `hotfix/内容` | 展示中など、緊急の修正用 |

**運用ルール**

- 作業を始める前に、現在のブランチが作業内容に合っているかを確認する。
  合っていなければ適切なブランチ（`feature/機能名` など）の作成と切り替えを提案し、**了承を得たうえで**実行すること。
- 変更を行うたびに**自動でコミットし、プッシュまで行う**こと。コミットメッセージには、何をしたかが分かる内容を書くこと。
- `develop` へのマージはAIが行ってよい。
  **`main` へのマージは展示に出す版に直結するため、実行前に大槻 海斗（GitHub管理担当）の確認を取ること。**
- コンフリクトが起きた場合は**勝手に解決せず**、どのファイルのどこが衝突したかを分かりやすく説明し、対応方針を確認すること。
- メンバーがGitの操作方法を尋ねてきた場合は、Git Flowの流れ（`feature` → `develop` → `release` → `main`）とあわせて丁寧に説明すること。
- 指示があれば、コミットを行わない、別のブランチで作業するなど、**その指示を優先する**こと。

**Unity特有の注意（重要）**

- シーン（`.unity`）とプレハブ（`.prefab`）は自動マージができないため、これらを編集した場合は**その旨を必ず報告する**こと。
- 同じシーン・同じプレハブを**2人以上が同時に編集しない**。編集前に連絡手段で「今からこのシーン触ります」と一声かける運用とする。
- 衝突すると片方の作業が失われるため、シーン作業は短時間で終わらせ、こまめにプッシュすること。

### 実装時の記録

- 実装を指示された時、実装について詳しく聞かれない場合は、**誰でもわかるように機能の説明だけ**を行うこと。
- 追加した機能の詳細は `Documents/機能ドキュメント/` に**1機能1ファイル**として追加すること。
- あわせて `Documents/制作ログ.md` に、**日付・担当者・追加した機能・誰にでもわかる簡易的な説明**を追記すること。

### コードの方針

- プログラムの安全性やきれいさよりも、**実装できるかどうかを優先**し、複雑なコードにしないこと。
- ただし、**他の人が編集中のファイルには手を加えず**、新しい機能はできるだけ新しいファイルに書くこと。
- 指示があれば安全性や拡張性、きれいさも意識すること。
- 動作を優先した結果、安全性に懸念が残る実装になった場合は `Documents/リスクリスト.md` に**リスク度とその内容**を記載すること。
- 入力処理は **Input System**（`Assets/InputSystem_Actions.inputactions`）を使う。旧来の `Input.GetKey` 系は混在させない。

#### シーンとプレハブの作り方（重要）

> 📄 詳しくは **`Documents/シーンとプレハブの作り方.md`** を読むこと。

シーンは自動マージができず、2人が同時に触ると片方の作業が消える。
そこで、**そもそも同じシーンを2人が触らなくて済む形**にする。

1. **1つのシーンには1つの機能だけを作る。** 機能ごとに専用のシーンを新しく作る
2. **そのシーンを再生するだけで、その機能だけをテストできる**ようにする
3. **完成したらプレハブにし**、他のシーンに置くだけで動く状態を目指す（**目標であって義務ではない**。無理にプレハブ化して複雑になるくらいならしなくてよい）

検証用シーンは残しておくが、**製品のビルドには含めない**こと。

### バグ対応

1. 複数のファイルにまたがるバグが発生し、原因がすぐに分からなかった場合は、まず `Documents/リスクリスト.md` を確認し、そこに原因がないか探る。
2. 該当しそうな記載がなければ、AI自身でデバッグを行い原因を探す。
3. ユーザーの操作が必要な場合は、**丁寧な手順を提示する**こと。

### ファイル操作の禁止事項

> ⚠️ `Mirai01/Assets/` 以下のファイルを、**OS側でのファイル操作によって移動・リネーム・削除しないこと。**

Unityは `.meta` ファイルで各アセットの参照を管理しているため、これらの操作を行うと**プレハブやシーンの参照が外れる**。
必要な場合は実行せず、Unityエディタ上で行う手順を提示すること。

### セキュリティ

- APIキーやパスワード、個人情報をコードやドキュメントに書かないこと。

2. **責任は制作者本人が負う。** 作品内容・権利・倫理・社会的影響の責任は、AIを使った場合でもすべて本人にある。
3. **各サービスの利用規約を守る。** 使う前に、その生成AIサービスの規約を確認する。

また、**権利侵害・誤認を招く表現・人権や倫理上の問題・プライバシー侵害・公序良俗に反するもの**は
会場展示もHP掲載も認められない。詳しい条件は `Documents/使用素材とライセンス.md` にまとめてある。

### 生成AIの使用基準（このプロジェクトでの運用）

| 対象 | 基準 |
| --- | --- |
| **デザイン・グラフィック** | 生成AIの出力をそのまま使用せず、**加工を施したうえで**使用すること |
| **プログラム** | 担当者がそのコードの**意図と動作を説明できる状態**であれば使用してよい |

理解できないままコードを組み込まないこと。バグが出た時に対応できなくなる。

判断に迷う場合はプロジェクトリーダーに相談すること。
